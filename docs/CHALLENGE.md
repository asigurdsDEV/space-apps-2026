# Challenge: Space Mission Design Game

**Team:** Kimchi Trenchers (Aiden, Ethan, Jamie, Sarah, Caleb (kimchi on the team page), Kaipo) · **Local event:** Seattle, WA · **Event:** NASA Space Apps 2026 (Nov 14–15)
**Official page:** https://www.spaceappschallenge.org/2026/challenges/space-mission-design-game/
**Difficulty:** Intermediate, Beginner/Youth · **Subject:** Games

> This is our team's paraphrase of the brief, to help agents and humans build against it. The official page is the source of truth, so check it before you quote anything.

## The ask, in one paragraph

Build an interactive game where students design, manage and **simulate a complete space mission**, from concept through operation. Players make engineering decisions under limited resources and see how each choice changes whether the mission succeeds. Real mission design is a web of trade-offs. For example, a better instrument means more science, but also more mass, power, data and cost. Students rarely get to try a whole mission end to end, so those trade-offs stay abstract. The game should make them concrete.

## What a strong entry has (from the Objectives section)

1. **A working, playable game or simulation** with a clear UI.
2. **Mission configuration:** objective → requirements → spacecraft → instruments → launch vehicle → orbit.
3. **Resource management** across the core resources below, shown clearly at all times.
4. **Simulation + evaluation:** run the mission, score it, and explain the result.
5. **Collaboration / multiplayer for up to 4 players**, optional but called out explicitly in the brief.
6. **Feedback that teaches:** reward good engineering, efficient resource use, teamwork and meeting objectives, and explain *why*, not just pass/fail.

## Core resources the game should track

| Resource | Meaning |
|----------|---------|
| Mass | Total spacecraft + payload mass; must fit the launch vehicle |
| Power | Energy available to run systems and instruments |
| Budget | Money to build and operate the mission |
| Data | Volume generated by the instruments |
| Communications | Capacity to downlink that data to ground stations |
| Time | Development schedule + operational lifetime |

The brief says we may choose which of these matter most for our mission scenarios.

## Design hints from "Potential considerations" (all optional)

- **Every major decision has a consequence** that ripples into other resources.
- **No single right answer:** several spacecraft/instrument/orbit/launcher combinations can meet the same objective.
- **Spacecraft components:** structure, power/batteries, comms, onboard computer, attitude control, instruments. Simple vs. advanced parts could vary by difficulty.
- **Instruments** each have mass, power, cost, data rate and science value.
- **Orbits:** several options, each affecting coverage, observation opportunities, comms and lifetime.
- **Launch vehicles:** different capacity, cost and orbit reach. **Check that mass and orbit are compatible with the launcher.**
- **Team mode:** up to 4 roles (e.g. mission planning, spacecraft, science, comms/resources) that must negotiate priorities.
- **Accessible to novices:** introduce concepts like orbital altitude, payload capacity and data rate inside the game (tooltips, short explainers, visual indicators).
- **Replayable:** edit the design and re-simulate.

## Nice-to-have features they list

Multiple scenarios · random events · difficulty levels · spacecraft visualization · live resource dashboard · leaderboard · end-of-mission report · save/share/compare designs · co-op for 4 · competitive mode · sandbox · post-mission "why it failed" analysis.

## How this maps to our repo

The repo is already set up for a simulator (see `.agents/CONTRACTS.md`, v0.1 in PR #2):

- **`sim/`**: the pure mission simulator. `init(config)` builds the mission from the player's design, and `step(state, commands)` advances the mission phases (launch → cruise/orbit insertion → operations → end of life) and emits events like resource shortfalls and random failures. `summary(state)` produces the score and the post-mission explanation.
- **`data/`**: catalogs of parts (instruments, buses, power, comms), launch vehicles, orbits and scenarios, with numbers loosely grounded in the NASA references below.
- **`ui/` / `app/`**: the design screens, resource dashboard, mission playback and end report.
- **Stack:** TypeScript + Vite + React static app (decision 002, PR #3, claude@aiden). With no backend, the up-to-4 team mode would be pass-and-play.

## NASA resources listed on the challenge page

- [Design and Develop Science Missions (PDF)](https://www.nasa.gov/wp-content/uploads/2025/04/250323-design-and-develop-science-mission.pdf): systems-engineering overview; launch / space / ground / user segments.
- [General Mission Analysis Tool (GMAT)](https://software.nasa.gov/software/GSC-19468-1): open-source trajectory and mission analysis. Overkill to embed, but a good place to sanity-check orbit numbers.
- [Concept Maturity Levels (JPL)](https://dataverse.jpl.nasa.gov/dataset.xhtml?persistentId=hdl:2014/44299): CML 1–4 stages; a possible structure for the game's phases.
- [Mission Design Lab (GSFC)](https://etd.gsfc.nasa.gov/capabilities/integrated-design-center/mission-design-lab/): how NASA runs concept studies and trade studies; the subsystem list is a good component checklist.
- [NASA Mission Viz](https://nasa.github.io/mission-viz/): web-based mission visualization.
- [A Learning Game About Telescopes (Webb)](https://science.nasa.gov/mission/webb/game-build-it-yourself/): an existing NASA build-it game for comparison.
- [CubeSat 101 (PDF)](https://www3.nasa.gov/sites/default/files/atoms/files/nasa_csli_cubesat_101_508.pdf): realistic small-sat mass, power and cost figures for a beginner scenario.
- [Visualize a Space Mission Using VR (2023 challenge)](https://www.spaceappschallenge.org/2023/challenges/visualize-a-space-mission-using-virtual-reality/)
- [CSA Digital Games and Activities](https://www.asc-csa.gc.ca/eng/youth-educators/digital-games-and-activities.asp)
